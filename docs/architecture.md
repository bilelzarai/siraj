# Sirāj v2 — Backend architecture

Oct 8, 2026 · exported from the "Sirāj v2 — Backend architecture" doc on claude.ai (diagrams are in the online doc).

## Overview

One Go binary serves the website (templ + htmx) and a JSON API for the mobile app from the same service layer, on one PostgreSQL 18 database. The web pages and the API never touch SQL directly: both call a feature module, which calls sqlc-generated queries.

| Concern | Choice | How it is used here |
| --- | --- | --- |
| HTTP | Gin | One router: HTML routes at `/`, JSON at `/api/v1`, realtime at `/ws` |
| Database | PostgreSQL 18 via pgx/v5 | One `pgxpool`, transactions per use case, `LISTEN/NOTIFY` for realtime fan-out |
| Queries | sqlc | One `.sql` file per module, generated Go in `internal/db/sqlc` (never edited) |
| Migrations | golang-migrate | SQL files embedded with `embed.FS`, applied on startup before the server listens |
| HTML | templ | Layouts, components and pages; htmx partials are plain templ components |
| Frontend build | Vite 8 (Rolldown) via Bun | Builds `web/assets` into hashed files + `manifest.json`, embedded in the binary |
| CSS | Tailwind CSS v4 | `@tailwindcss/vite`; the design tokens from the v2 prototype become `@theme` variables |
| Interactivity | htmx + Alpine.js | htmx swaps server-rendered partials; Alpine holds local UI state (timer, pager, recorder) |

Every request, from a page or the app, goes router → feature module → sqlc → PostgreSQL; the worker writes to the same database on a schedule.

Decisions that shape everything below:

- **Guests are real users** (`users.kind = 'guest'`, with `expires_at`). Games, rooms and challenges work for them with the same tables, and upgrading to an account keeps the same id, so points carry over.
- **Every text a player reads exists in 3 languages** through `*_translations` tables keyed by `(id, lang)`. Adding a language is one row in `languages`.
- **A game is one model for every mode** (solo, live room, duel, challenge, on this device): `games` + `game_players` + `game_questions` + `game_answers`.
- **UUID v7 for anything a client sees** (users, games, rooms, messages), `bigint` for content numbered in the UI (question #604).
- **Realtime state lives in memory, results live in Postgres.** A room's live state is held by the hub; every answer is written, and `LISTEN/NOTIFY` keeps several server instances in sync.
- **A player's app is scoped to Your domains.** `user_domains` (at least 1 row per player) drives Home, Play, game setup, search, mastery, leaderboard filters and the question of the day. Only Explore, Add a domain and onboarding list every domain; playing in a domain that isn't yours adds it first.
- **Neutral shell, themed domains.** Each domain carries its own `family` (islamic/general), colour, icon and motif; the Islamic geometric style is used only inside the Islamic family. `user_settings.islamic_only` hides every general domain and keeps the app as it was in v1.

## How the laptop, the backend and the database talk

The laptop never connects to PostgreSQL. It talks HTTPS (and a WebSocket during live games) to the Go server, and only the Go server, from inside the private network, talks to the database.

Example: a player answers a question. htmx sends the answer, the server checks the session, the games module saves it with one SQL call, and the server sends back only the feedback panel, which htmx swaps into the page.

| Hop | Protocol | What travels | What protects it |
| --- | --- | --- | --- |
| Laptop → Go server | HTTPS on 443 (TLS ends at Caddy or Nginx), WebSocket on `/ws` for rooms and duels | htmx request + session cookie; the mobile app sends JSON + `Authorization: Bearer` | TLS, session check, CSRF token, rate limit |
| Gin → feature module | A Go function call inside the same process | Typed input, e.g. game id, question, choice, time | The service enforces game rules |
| Module → PostgreSQL | PostgreSQL wire protocol over TCP 5432, connections reused from the pgx pool | Parameterised SQL generated by sqlc (no string-built SQL) | Private network only, DB user with minimum rights, TLS to the DB |
| PostgreSQL → laptop | Same path back | Rows → Go structs → HTML fragment (web) or JSON (mobile) | Only DTO fields leave the server |
| Server → other servers | `LISTEN/NOTIFY` on PostgreSQL | Live events when several servers run | Same private connection |

On your laptop during development, the same three pieces run locally:

1. `docker compose up -d` starts PostgreSQL 18 on `localhost:5432`.
2. `.env` holds `DATABASE_URL=postgres://siraj:secret@localhost:5432/siraj?sslmode=disable`.
3. `make dev` starts the Go server on `http://localhost:8080` (it runs migrations first) and Vite on `:5173` for assets with hot reload.
4. Open `http://localhost:8080` in the browser; the page loads its CSS and JS from Vite.
5. To look inside the database, point TablePlus, DBeaver or `psql` at `localhost:5432`. In production you reach it only through an SSH tunnel or the hosting provider's console, never from the open internet.

## PostgreSQL database

61 tables in 10 modules, one `public` schema, one migration file per module. The game tables are the hot path; everything else is ordinary CRUD.

### Conventions

- **Keys:** `uuid DEFAULT uuidv7()` (built into PostgreSQL 18) for client-visible rows; `bigint GENERATED ALWAYS AS IDENTITY` for questions, catalog and lookups; composite keys for join tables.
- **Columns on every table:** `created_at timestamptz NOT NULL DEFAULT now()`, `updated_at` where rows change (one shared trigger), `deleted_at` only where content must be restorable (questions, sets, messages).
- **Languages:** `languages(code text PK)` holds `ar`, `en`, `fr`; every `*_translations` table has `PRIMARY KEY (parent_id, lang)` and `lang REFERENCES languages`.
- **Enums** for closed sets: `user_kind`, `user_role`, `game_mode`, `game_status`, `question_status`, `challenge_status`, `conversation_kind`, `ticket_topic`, `ticket_status`, `sanction_kind`, `review_decision`, `notification_kind`.
- **Money of the game is integers:** points, XP, ratings, milliseconds. No floats in scoring.
- **Foreign keys always,** `ON DELETE CASCADE` from a user to their personal data, `RESTRICT` on content other players depend on.
- **Extensions:** `pg_trgm` (fuzzy search, duplicate detection), `unaccent`, `citext` (usernames, emails).

### Performance and housekeeping

- **Hot paths:** picking questions = partial index on published questions by category and difficulty; message threads = cursor on uuid v7; unread badges = `last_read_message_id` comparisons, never counts over all messages.
- **Partitioning:** `game_answers` by month from day one; `messages` and `notifications` can follow when they pass ~50 M rows.
- **Search** (100 domains, the topic picker, admin): trigram GIN indexes on translation names and question bodies, queried with `ILIKE` / `%` plus `unaccent`.
- **Worker jobs:** delete expired guests and their data (cascade), close idle rooms, expire challenges and links, refresh leaderboard views, detect duplicates, send reminders.
- **Transactions:** finishing a game writes players, stats, XP, activity, leaderboard and achievements in one transaction.

Rules that keep it clean:

- **Dependency direction:** handlers → service → `sqlc.Queries`. Handlers never import `sqlc`; services never import Gin or templ. That is what lets `web.go` and `api.go` share one service.
- **One handler pair per screen:** `web.go` returns a full page or, when `HX-Request` is set, only the partial; `api.go` returns JSON DTOs from `dto.go`, never sqlc rows.
- **Generated code is never edited:** `make gen` runs `sqlc generate` and `templ generate`; CI fails if the output is stale.
- **Dev loop:** `make dev` runs `templ generate --watch`, `bunx vite` (assets with hot reload) and `air` (Go) together.
- **Migrations:** `make migrate-new name=x` creates a numbered up/down pair; the server applies pending ones at startup and refuses to start on a dirty state.
- **Design kit mapping:** the class names and tokens in `app.css` from the v2 prototype become Tailwind `@theme` tokens + component classes, and each prototype screen becomes one templ page.

## JSON REST API (mobile app and other clients)

117 endpoints in 14 groups under `/api/v1`, all calling the same services as the website. Admin stays web-only for now; it can get `/api/v1/admin/*` later without touching these.

### Conventions

- **Auth:** `Authorization: Bearer <token>` from endpoints 1–6; guests get a token too (endpoint 4). The role decides access, not the URL.
- **Language:** `Accept-Language: ar | en | fr` picks the language of every question, category and message returned.
- **Responses:** `{ "data": … }`, lists add `"page"` or `"next_cursor"`; errors are `{ "error": { "code", "message", "fields" } }` with proper HTTP status.
- **Scope:** domain lists, search, mastery and the question of the day default to the player's domains (`?scope=mine`); `?scope=all` is only for Explore, Add a domain and onboarding. A game scope of `all` means all of the player's domains.
- **Paging:** cursor (`?before=`) for feeds (messages, notifications, history); page numbers (`?page=&per_page=`) for lists (domains, mastery, sets).
- **Safety:** `Idempotency-Key` header on answers and creates; rate limits per token; ids are uuid v7 except questions, domains and categories.
- **Dates:** ISO 8601 in UTC; durations in milliseconds.

## Admin back office

The admin is web-only (templ + htmx under `/admin`), on the same services and tables as the player app, and every staff write lands in `audit_log`. Its design is the Sirāj Admin Console in `docs/design-admin` (12 screens), now on the v2 neutral shell with lamp gold; the Domains screen manages each domain's family, colour, icon, motif, flagship and "New" badge.

| Screen | Route | What staff do there | Tables | Who |
| --- | --- | --- | --- | --- |
| Dashboard | `/admin` | KPIs, games per day, category performance, needs attention, players by domain and by language, recent activity | `daily_activity`, `games`, `user_domains`, `question_reviews`, `support_tickets`, `audit_log` | All staff |
| Users | `/admin/users` | Search, role, the player's domains and Islamic-only setting, warn / suspend / ban, moderation history | `users`, `user_settings`, `user_domains`, `user_sanctions` | Moderator, admin (roles: admin only) |
| Support | `/admin/support` | Inbox by topic, reply, resolve | `support_tickets`, `ticket_messages`, `ticket_attachments` | Support, admin |
| Domains | `/admin/domains` | Create and edit family, colour, icon, motif, flagship, "New" until, order, live | `domains`, `domain_translations` | Admin |
| Categories | `/admin/categories` | Create, edit, order, retire | `categories`, `category_translations` | Admin; translator for text |
| Questions | `/admin/questions` | Filter by domain, category, level and coverage; edit in 3 languages; publish, retire, CSV import | `questions`, `question_translations`, `question_revisions` | Moderator, admin; translator for text |
| Review queue | `/admin/review` | Approve, reject or send back (keys A / R / E / S) | `questions` (status review), `question_reviews` | Moderator, admin |
| Comments | `/admin/comments` | Hide, mark resolved, dismiss reports | `question_comments`, `comment_reports` | Moderator, admin |
| Rated poorly | `/admin/rated` | Questions with low stars and their reasons; send to review | `question_ratings` | Moderator, admin |
| Content health | `/admin/health` | Checks, possible duplicates (merge or mark different), translation coverage | `question_duplicates`, `question_translations` | Moderator, admin |
| Audit log | `/admin/audit` | Every staff write, filtered by person, action and date | `audit_log` | Admin |

| Role | What it can do |
| --- | --- |
| player | The app only |
| translator | Edit question and category text in the 3 languages; cannot publish |
| moderator | Translator rights, plus the review queue, publish and retire questions, comments, rated poorly, content health, warn and suspend players |
| support | The support inbox, and read-only user profiles |
| admin | Everything, including domains, categories, roles, bans and the audit log |

- Every `/admin` route needs a session whose role is not `player` (`RequireRole` middleware); each handler then checks the role it needs.
- Every staff write records `audit_log` (actor, action, entity, diff) in the same transaction as the change.
- Publishing or retiring a question refreshes `categories.question_count`; moving a domain to the general family hides it for players with Islamic content only.
- An active suspension or ban (`user_sanctions`) blocks sign-in and revokes the player's sessions.
- An admin JSON API (`/api/v1/admin/*`) can come later; the screens use htmx partials.

## Build order

Build in 7 steps, each one shippable, the riskiest piece (realtime) after the solo game works end to end.

1. **Skeleton:** repo layout, config, `pgxpool`, embedded migrations, Vite + Tailwind + templ wiring, `/health` (113).
2. **Identity and catalog:** modules 1–2 of the database, auth incl. guests (1–16), domains, your domains and search (17–23, 114–117).
3. **Solo game:** questions, games, scoring, results, ratings and reports (24–35); the web pages from the v2 kit.
4. **Progress:** XP, mastery, streaks, leaderboards, history (31, 90–95).
5. **Realtime:** hub + `/ws` (111), live rooms (36–46), duels (47–50).
6. **Social layer:** challenges (51–62), friends (63–74), messages (75–86), notifications (87–89).
7. **Player content and support:** my questions (96–105), support tickets (106–110), then the admin back office on the same tables.

Open questions to settle before step 2:

- Does v1 already have users and questions in a database that must be migrated, or does v2 start clean?
- Where do uploads live in production (S3, Cloudflare R2, local disk)?
- One server instance at launch, or several behind a load balancer from day one (decides whether `LISTEN/NOTIFY` is needed now)?
- A guest or new player who skips onboarding still needs at least one domain: default to Islamic Knowledge only, or to the 3 most played?
- When Islamic content only is on, do general domains stay in `user_domains` (hidden) or get removed?
